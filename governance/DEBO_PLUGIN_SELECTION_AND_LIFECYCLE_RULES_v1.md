# DEBO Plugin Selection and Lifecycle Rules v1.0 — 2026-11-03

Status: SOURCE POLICY. Applies to DEBO Core and sister-brain adapters. Existing DEBO bootstrap, JARVIS risk gates, owner approvals and source-system permissions override any convenience rule here. Documentation does not itself install, enable, connect, schedule or deploy software.

## 1. Automatically choose the best authorized tool at task time

Recover the mission, project, current checkpoint, intended output, data classification and applicable approval gate. For private facts, query the correct connected provider/Files/Library/Notion/GitHub before generic web search. For current public information use ChatGPT Search with sources; use Deep Research for complex multi-source investigations; use installed Firecrawl for permitted multi-page public extraction; use Work or TinyFish for supported interactive sites; use GitHub/Python/Codex for reproducible code and tests. Do not send protected private data to general public-search services.

Reuse the smallest effective existing authorized tool. Prefer read-only actions, reduce redundant searches, honor rate limits and stop repeated failed calls. Choosing an already-authorized read tool inside this conversation needs no fresh plugin sales pitch. External writes, sending, spending, public release, deployment, deletion, account/permission changes and sensitive records remain governed by applicable approvals.

Separate six observations: DISCOVERED, INSTALLED, CONNECTED, AUTHORIZED, CALLABLE, TESTED, LIVE. A plugin may be installed but the intended account disconnected or resource forbidden. Neither an ACTIVE registry label nor a previous synthetic test proves live service. Record UNKNOWN instead of pretending a missing read is a missing system.

## 2. Suggest a missing plugin only when its advantage is meaningful

If existing tools do not meet the actual requirement, search Plugin Management before recommending a manual workaround. Compare project fit, source quality, cost/limits, privacy, required account connection, maintenance, permissions, duplicate coverage and measurable task value. Recommend only a relevant available plugin and say exactly why and what user action is required. Do not suggest the same plugin again within seven days unless the user explicitly asks. Installing or connecting a plugin requires the user's explicit action; never silently grant accounts or new permissions.

Prioritize closing a documented workflow gap, not maximizing installed app count. Optional external software evaluations can use G2 reviews; optional traffic estimates can use Similarweb, but only when public Search and existing tools cannot establish the answer. Check pricing and access before use and make no spend assumptions.

## 3. Update, reuse, merge or retire existing tools and skills

Check the existing DEBO Skills Registry and current runtime before creating a new skill. Decide USE / UPDATE / MERGE / SUGGEST / BUILD ADAPTER / HOLD / RETIRE. Update an existing adapter for verified changed API/tool capabilities, source drift, recurring failures or material gains. Preserve one canonical GitHub source, versioned private skill release, dependency checks, project isolation, regression and negative authorization tests, CI status, readback and rollback.

A new skill is justified by a repeated or consequential gap with clear inputs, outputs, permissions, tests and net benefit. Do not copy all project-specific SKILL.md files into DEBO Core. Do not create another master brain, CRM, registry or dashboard when a canonical system exists. Retire only after proving replacement coverage and preserving historical records.

## 4. Reuse the existing weekly DEBO System Scout

The current enabled DEBO System Scout already checks plugins, APIs, reusable code, gaps and upgrades. Retain its existing schedule and previously settled approval/privacy rules. Do not create another scout or modify it merely to restate the same instructions. Its output should include: project, source and checked date, exact job, current installed/connected/authorized/tested status, existing alternative, cost/security, proposed decision, owner approval, verification test, rollback and one next action. Weekly scans are not continuous execution.

For a future recurring event first inspect existing Scheduled tasks and latest runs. Event-based ChatGPT Work tasks require supported triggers, actual account connection, authority and user setup. A previous successful task run does not prove future success. Never promise unsupported direct Notion or Drive event triggers or bypass a 403/404 provider gate.

## 5. Practical route map

| Task need | Preferred current route | Conditional upgrade |
|---|---|---|
| Restore threads, decisions, file context | ThreadOps, current DEBO checkpoint, authorized Files/Library and Notion | Recover permissions/sources, not a new brain |
| Fresh public facts, codes, research | ChatGPT Search + original official sources | Deep Research for complex multi-source uncertainty |
| Public multi-page extraction | Installed Firecrawl, appropriate TinyFish/Work | Only if terms, privacy and access permit |
| Private ClaimEdge/JCT operations | Correct approved CRM/Drive/CompanyCam or project system | Domain adapter only, preserve owner gates |
| Code and regression | GitHub Actions, Python, existing auditor, Codex as needed | Small tests/repair before new package |
| Sales pipeline and local marketing | Existing HubSpot/Airtable/Apollo/Metricool, only appropriate canonical account | Similarweb or specialty analytics on proven gap |
| Software buying decisions | Search, official docs, repo issues and source/license checks | Optional G2 review data after comparison |
| Design and mobile dashboard | Existing Figma, Canva, MagicPath and design tools | No new design app absent specific limitation |
| Scheduled updates | Existing DEBO System Scout, Morning Brief and project watchers | New task only for a distinct authorized future hinge |

## 6. Tool decision receipt and verification

Record material decisions using fields: mission_id, project_id, task, existing_tools_checked, chosen_tool, installed, connected, account_scoped, authorized, data_class, sources_and_checked_at, action_risk, result, test_and_readback, cost_if_known, alternative, decision, saved_checkpoint, next_action.

A task is complete only when its actual required behavior is observed, its output checked and the appropriate existing project checkpoint saved/read back. Track actual time saved, source coverage, error reductions, cost and rework when measured; do not turn estimates into measured ROI.

Known boundaries: JCT public/financial changes require John; ClaimEdge submission/review follows Susan and other applicable authority; protected youth/client/financial records stay out of public repositories or uncontrolled handoffs. No new permissions, spend, public launch, deletion, outreach, provider bypass, new schedule or production mutation is authorized by this rule.
