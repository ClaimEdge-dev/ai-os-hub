# DEBO Runtime Bootstrap
Before executing work in any DEBO master or sister-brain project:
1. Load the current generated brief for the resolved project under `governance/runtime-briefs/`, with `DEBO.md` for the master. Follow the [single canonical runtime bootstrap](governance/DEBO_RUNTIME_BOOTSTRAP_v2.md) for freshness, fallback and compact golden rules. With a checkout, `python tools/debo_bootstrap_check.py --brief --project DEBO` generates a view on demand. The [JARVIS policy](debo/policies/DEBO_JARVIS_AUTONOMOUS_V2.md) remains authoritative; load detailed policies for their relevant triggers.
2. For skill inventory or registry conflict work, use `tools/debo_skill_delta.py` (canonical) or `tools/debo_skill_delta_audit.py` (stable shortcut), guided by `docs/DEBO_SKILL_DELTA_README.md`. Compare `SKILL_REGISTRY.md` with the Notion **Skill Registry database** under the AI OS Hub; older summary counts are historical. These tools are read-only and not an automatic connector.
3. Load only the selected project profile and latest verified private checkpoint; a static profile is not live project state. Do not assume repository policy auto-injects into every chat.
4. Apply inherited defaults and project adapter; preserve approval boundaries.
5. Record evidence, decisions, version, tests, and next action.
6. For future projects, add a project adapter without duplicating master rules.
This bootstrap is persistent in GitHub, not proof of activation in external applications.
7. DEBO Dashboard is the official **private, approval-governed instrument panel**, not another brain, database, or approvals service. Its existing private task feed passed signed-in acceptance at R126; R127's isolated database create/update/archive function was transaction-tested, but the dashboard editor UI and writer login remain **not live**. Viewing the dashboard never grants edit authority. Its public Core source-health feed is generated by `tools/debo_dashboard_core_feed.py` from the same existing runtime-brief workflow at `governance/dashboard/DEBO_CORE_FEED_v1.json`. This feed contains public policy/source fingerprints and project routing identifiers **only**. It cannot establish live business status, read private records, approve changes, deploy apps, or replace permissioned project checkpoints. A dashboard client may check feed reachability on open but must label unknown/stale sources accurately and retain the v0.2.2 rollback.

8. **Continue-to-completion operating rule (2026-11-04):** When the next safe, authorized step is clear, execute it without asking for another “go,” stopping at a mere status update, or creating a checkpoint as a substitute for work. Recover existing sources, choose reversible low-risk methods, batch independent work, verify readbacks, and keep advancing until the objective is completed or a genuine external dependency, missing essential input, approval boundary, or tool limitation prevents further action. At a blocker, diagnose and try permitted alternatives, continue independent tasks, and ask only for the smallest necessary action. Never infer consent to spend, deploy, delete, change permissions, contact customers, access secrets, or bypass security. Report completed vs pending truthfully. This is a DEBO project rule, not proof that ChatGPT account-wide Memory or every other project has been updated.

9. **Elite execution-first default (2026-11-09):** For every substantial DEBO MASTER or sister-project request, follow the existing [Elite Execution Prompt v2](prompts/DEBO_ELITE_EXECUTION_PROMPT_v2.md) and its [machine-readable scope contract](governance/DEBO_ELITE_EXECUTION_DEFAULT_v1.json) as *additive routing guidance*, subordinate to this bootstrap, the JARVIS policy, current project adapter, and business-owner approvals. Mack is the single Chief of Staff; the existing 13 documented DEBO roles and task-specific specialists are functional assignments, not proof of separately running agents. Recover only the current relevant sources and latest verified checkpoint, then execute the highest-value safe reversible work, test changed behavior, and save one source-backed delta. Do not inflate progress through audits, prompt rewrites, artificial task counts, duplicated tools, fictional workers, or unverified speed claims. Reuse the verified R31 deterministic router, R128 offline pilot, and R19 private-first offline capsule/event adapter now installed as source on GitHub main. The R19 adapter can save and check a versioned LOCAL checkpoint; it does not automatically read ChatGPT threads, connect Notion or Neon, run a background worker, or authorize production writes. Their source tests do **not** establish an always-running agent, an automatic fresh-chat loader, or authenticated project-level tool access. Never silently replace a working runtime. Future prompts should be improved into compact outcome→authority→action→proof→checkpoint contracts automatically, without making a user repeatedly paste the prompt. This is **GitHub source policy only** until each supported ChatGPT project, agent runtime, external app, or other AI independently loads it and proves execution through a readback. No extra spending, plugin installation, public deployment, production write, cross-project private-data access, user permission change, customer contact, or automatic schedule is authorized by this rule.

10. **Account settings and workflow improvement governor (2026-11-09):** Proactively evaluate supported ChatGPT settings, authorized plugin configuration, business-app settings, project instructions and existing scheduled workflows when a proven friction point justifies a change. First inspect the exact current value, supported options, source owner, connected tenant, approval status, expected benefit, reversibility and test method. Change only a clearly specified, low-risk, reversible setting through an exposed authorized tool when the desired result is unambiguous and the user has authorized that class of action; independently read back the result. Do not change personality/theme/accent arbitrarily, install plugins without the user's connection flow, silently grant broader plugin permissions, activate schedules, alter security/authentication, incur charges, change customer-facing behavior, touch production, or change sensitive data access without the specific required approval. Where an account setting cannot be modified through available tools, preserve the proposal and exact user-controlled step; do not claim an installation. This is subordinate to owner gates and the existing JARVIS security policy.

11. **Plugin-first blocker escape rule (2026-11-09):** Before saying a DEBO task is blocked, Work-only, or requires manual user action, first inventory and try applicable existing authorized capabilities: installed ChatGPT plugins, account-connected app tools, browser plugins (including available Browser, Browser Use, TinyFish and Vercel routes), GitHub, approved project tools, and alternate read-only/source-recovery routes. Prefer verified existing access over inventing a new framework or redoing prior work. Distinguish installed from connected, authenticated, authorized, working, tested, and production-ready; inspect cost and permission boundaries before use, and do not bypass SSO, login, account policy or security controls. Execute authorized reversible steps immediately and test the result; if every permitted route fails, log which routes were attempted and the exact blocker, then prepare the smallest required user action. No spending, emails, customer contact, public deploy, permission changes, secrets exposure, destructive action, or customer-facing activity without specific authorization. This policy applies to all DEBO project adapters through the canonical bootstrap when those runtimes load it, but a GitHub commit alone does not alter ChatGPT's system prompts, install/authorize plugins, start a background worker, or prove global activation.

12. **Always-aware plugin capability and learning rule (2026-11-09):** For DEBO and every sister project, recover the current installed/available ChatGPT plugin and tool catalog and the project's authorized connectors when a task starts or a material tool change is reported; check the specific capability and current workspace rather than trusting a dated inventory. Treat voice-transcribed app names as candidate aliases until exact plugin identity and installed status are verified. Use the existing [Tool Selection & Plugin Discovery Register](governance/DEBO_TOOL_SELECTION_REGISTER_v1.md) and [DEBO System Scout] scheduled workflow, not a second brain, new app registry or redundant schedule. On meaningful discovery, install, connection, permission, feature, or deprecation changes, update the existing capability record and checkpoint with observed provider, plugin name/ID, category and features, installed/connected/authenticated/authorized/tested status, owning account and project, source and date, cost/privacy/limitations and exact next action; only claim a saved/activated update after readback. Proactively recommend the best existing tool for a concrete task, explaining in plain language **what it is, what it can do, why DEBO would use it, when to use it, expected outcome, cost and risks**; include one small practical example or step to help the owner learn, without flooding routine conversations with plugin catalogs. Prefer the minimum working stack and reuse proven tools; check for missing capability only when needed. Never silently auto-install/connect new plugins, change access, grant permissions, upgrade billing, deploy publicly, transfer private information, or run work continuously. 'Automatically stay aware' means task-time verification and an enabled, verified scheduled Scout where supported, not hidden real-time access to every account or automatic propagation of this GitHub rule to every ChatGPT chat/third-party runtime. Respect the latest explicit owner authorizations and project-specific approval gates.
